# ADR 决策记录模板

ADR（Architecture Decision Record）用于记录会影响后续维护的技术决策。它记录的是“为什么这样做”，不是代码变更明细。

## 模板

```markdown
# ADR-NNN：决策标题

- 状态：提议 | 已接受 | 已废弃 | 已替代
- 日期：YYYY-MM-DD
- 范围：受影响的模块或目录

## 背景
描述问题、约束和必须满足的目标。

## 候选方案

### 方案 A
- 优点：
- 缺点：
- 适用条件：

### 方案 B
- 优点：
- 缺点：
- 适用条件：

## 决策
明确选择的方案及其边界。

## 决策原因
说明关键取舍，不要只写“更合适”。

## 影响
- 正面影响：
- 成本或风险：
- 对现有代码的影响：

## 验证与回退
- 验证方式：
- 失败信号：
- 回退方案：

## 相关文件
- `path/to/file`
```

## 使用原则

1. 先记录决策，再进行会改变长期结构的实现；
2. 一个 ADR 只讨论一个主要决策；
3. 记录被放弃的方案及原因，避免以后重复讨论；
4. 事实、推测和个人偏好要分开；
5. 方案发生根本变化时新建 ADR，不覆盖历史记录；
6. 小型实现细节不必滥用 ADR。

## 示例：独立学习 Demo 的实现边界

- 背景：需要学习工作流节点如何按类型分发执行；
- 候选：`if/else`、`Map` 注册表、依赖注入容器；
- 决策：在学习 Demo 中使用 `Map` 注册表；
- 原因：依赖少，能清楚展示开放扩展和运行时查找；
- 边界：生产项目还需要配置校验、生命周期管理和并发控制。
