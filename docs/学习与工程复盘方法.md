# 学习与工程复盘方法

## 1. 知识分类

将学习内容分为四类，避免把事实、经验和待验证想法混在一起：

| 类别 | 记录重点 | 典型产物 |
|---|---|---|
| 原理知识 | 概念、机制、适用条件 | 原理笔记、源码阅读 |
| 实现知识 | API、代码结构、配置和命令 | Demo、代码片段 |
| 问题经验 | 现象、根因、修复和边界 | Bug 复盘、踩坑记录 |
| 设计决策 | 方案、取舍、影响和回退 | ADR、架构图 |

## 2. 学习输出闭环

对每个主题至少回答以下问题：

1. **场景**：在什么问题中遇到它？
2. **目标**：希望理解或解决什么？
3. **原理**：关键机制是什么？
4. **行动**：阅读了什么、写了什么、验证了什么？
5. **结果**：得到了什么可复现结论？
6. **边界**：哪些情况不适用，哪些内容仍未验证？
7. **迁移**：它能帮助当前哪个项目或代码文件？

只有“看过资料”而没有验证过程的内容，应标记为待验证，不要写成确定结论。

## 3. 代码学习的最小闭环

```text
提出问题
  ↓
建立最小模型
  ↓
实现可运行 Demo
  ↓
用输入、边界和异常验证
  ↓
记录结论与限制
  ↓
关联已有代码
```

代码 Demo 应尽量满足：

- 有单一明确主题，例如拓扑排序、变量解析或执行器注册表；
- 不依赖业务项目中的隐含配置；
- 有一个可以直接运行的入口；
- 把错误处理和边界条件作为学习内容，而不是只展示成功路径；
- 通过 README 说明它与其他学习目录的关系。

## 4. Bug 复盘模板

```markdown
## 问题
- 现象：
- 复现步骤：
- 预期行为：
- 实际行为：

## 根因
- 直接原因：
- 为什么会出现：
- 为什么原有检查没有发现：

## 修复
- 最小修复：
- 为什么没有采用其他方案：

## 验证
- 正常场景：
- 边界场景：
- 回归结果：

## 沉淀
- 可复用规则：
- 相关代码和文档：
- 后续待办：
```

## 5. 工程变更的记录边界

不是所有修改都需要完整的规格文档：

- 小型笔记修正：直接修改并保留准确注释；
- 独立 Demo：记录目标、运行方式和关键结论；
- 跨模块功能：补充计划、决策和验证结果；
- 有争议或影响长期维护的选型：使用 ADR；
- 尚未解决的问题：放入待办或问题记录，不伪装成完成结论。

## 6. 与当前仓库代码的结合方式

知识迁移不应只是复制文档，可以采用以下方式：

1. 将抽象概念实现成独立 Demo；
2. 将 Demo 与已有实现并排对照，不直接覆盖旧代码；
3. 在主题文档中链接 Demo、运行命令和验证结论；
4. 对不同技术栈明确标注差异，例如 MySQL 与 PostgreSQL；
5. 记录来源和改写范围，避免把原项目的业务上下文带入通用知识。
